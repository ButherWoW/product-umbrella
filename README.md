# Product Umbrella

Минимальный собственный трекер для рекламных кампаний.

Текущий MVP умеет:

- принимать tracking URL `/r/:campaign/:offer`;
- сохранять клик в локальный JSONL-файл;
- передавать click id и UTM-параметры на offer;
- принимать conversion postback через `/postback`;
- не требует внешних зависимостей.

Для защиты postback в локальной или серверной конфигурации задайте `POSTBACK_SECRET`. Тогда к URL нужно добавлять `secret`.

Для защиты управляющих API задайте `ADMIN_TOKEN`. При его наличии запросы `POST /api/offers`, `PATCH /api/offers/:id`, `POST /api/campaigns`, `PATCH /api/campaigns/:id`, `PUT /api/campaigns/:id/streams`, а также журналы `GET /api/clicks` и `GET /api/conversions` требуют заголовок `Authorization: Bearer <ADMIN_TOKEN>`.

Для защиты tracking routes от флуда доступны `CLICK_RATE_LIMIT` и `CLICK_RATE_WINDOW_MS`. При превышении лимита запрос получает `429`, новый клик не записывается.

Для production обязательно задайте `REQUIRE_LOGIN=1` и `ADMIN_TOKEN`. `TRUST_PROXY=1` включайте только за собственным reverse proxy; иначе IP нельзя считать доверенным из заголовка клиента.

Запуск:

```bash
npm start
```

Пример:

```text
http://localhost:4100/r/demo/offer-1?utm_source=facebook&utm_campaign=test
```

Это только локальный MVP. Перед production нужны PostgreSQL, авторизация, валидация offer URL, rate limits, приватность и защита postback.

Tracking URL принимает `utm_source`, `utm_medium`, `utm_campaign`, `utm_content` и `subid`.

Для stream-маршрута используется `/r/:campaign`. Пример тела: `{"streams":[{"offerId":"offer-1","weight":70}]}`.

Потоки с условиями (как в Keitaro):

```json
{"streams":[
  {"name":"ios","type":"forced","conditions":{"os":["ios"]},"offers":[{"offerId":"offer-a"}]},
  {"name":"de-mobile","conditions":{"countries":["DE"],"devices":["mobile"]},"offers":[{"offerId":"offer-b","weight":70},{"offerId":"offer-c","weight":30}],"weight":1},
  {"name":"rest","type":"fallback","offers":[{"offerId":"offer-1"}]}
]}
```

Порядок выбора: первый подходящий `forced` → взвешенный выбор среди подходящих `regular` → первый подходящий `fallback`; ничего не подошло — `404 no_matching_stream`. Условия: `countries`, `devices` (mobile/tablet/desktop), `os` (android/ios/windows/macos/linux/other), `browsers` (chrome/safari/firefox/edge/opera/samsung/other), `languages` (2 буквы из Accept-Language), `isps` (часть названия провайдера без учёта регистра, нужна база `GEOIP_ASN_DB`), `connections` (тип соединения: `mobile` / `broadband` / `datacenter`, тоже по базе `GEOIP_ASN_DB`, см. «GeoIP»). Без `GEOIP_DB` страна неизвестна, и поток с `countries` не срабатывает. Остальные условия и «НЕ» — ниже. Имя выбранного потока пишется в клик (`stream`).

Дополнительные поля потока (как в Keitaro):

- `enabled: false` — поток выключен и не участвует в выборе, но сохраняется.
- `countClicks: false` — редирект работает, но клик не пишется в журнал и отчёты.
- `action` — что делает поток: `offers` (по умолчанию, ротация `offers`), `url` (редирект на `url`, только https, макросы как у офферов; клик пишется с пустым `offerId`) или `not_found` (ответ `404 Not Found`, клик не пишется).
- `action: "campaign"` + `campaignId` — отправить клик в другую кампанию без редиректа: он проходит её потоки и записывается в ней (с `parentCampaign`). Не больше 3 переходов; цикл A → B → A → `508 campaign_loop`. Ограничения входной кампании уровня кампании (капы, IP-листы) не применяются — только её фильтры потоков.
- Кампания: `streamRotation: "weight"` (по умолчанию — обычные потоки делят трафик по весам) или `"position"` (клик забирает первый подходящий обычный поток по порядку), как «Ротация потоков» в Keitaro.
- Расписание потока: `conditions.days` (1 = пн … 7 = вс), `conditions.hours` (0–23), `conditions.tz` (IANA, неизвестный → UTC), например `{"days":[1,2,3,4,5],"hours":[9,10,…,21],"tz":"Europe/Paris"}`.
- `conditions.mode: "or"` — поток подходит, если сработал любой из заданных фильтров (по умолчанию все — «И»).
- Ещё условия (списки до 50 значений, строки до 200 символов; хранятся, только если заданы):
  - `referrers` — часть домена+пути реферера (без схемы и query), без учёта регистра: `["facebook.com", "instagram.com/ads"]`; без реферера не срабатывает;
  - `emptyReferrer: true|false` — реферер пустой / не пустой;
  - `keywords` — часть значения параметра `keyword` (после `paramMap` кампании), без учёта регистра;
  - `params: {"sub_id_3": ["fb","tt"], "source": ["push"]}` — точное совпадение отслеживаемого параметра после `paramMap` (поля как в «Параметрах»: `keyword`, `source`, `external_id`, `creative_id`, `ad_campaign_id`, `sub_id_1…30`); каждый параметр — отдельный фильтр;
  - `ips` — точный IP или IPv4 CIDR (`10.0.0.0/8`);
  - `userAgents` — часть строки User-Agent, без учёта регистра;
  - `dateFrom` / `dateTo` — `YYYY-MM-DD` включительно, в `conditions.tz` (или UTC).
- `conditions.not: ["countries", "referrers", …]` — «НЕ» (режим reject в Keitaro): перечисленные условия инвертируются — поток подходит, если посетитель НЕ попал в список. Работает и с «И», и с «ИЛИ». Неизвестное значение (нет GeoIP, нет реферера) под «НЕ» подходит. Например `{"countries":["US"],"not":["countries"]}` — все страны, кроме США.
- Условия только выбирают между потоками самой кампании; отдельных «белых/чёрных» страниц для ботов нет.
- `POST /api/simulate` принимает `referrer` и `query` (с учётом `paramMap`) и объясняет каждое условие: `{condition, expected, actual, ok, not?}`.
- Кампания: `redirectMethod` — `http` (302, по умолчанию), `meta` (страница с meta refresh) или `js` (location.replace + meta в noscript). URL в странице экранируется.

## Выгрузка CSV

`GET /stats/export?group=campaign|offer|stream|landing|country|sub_id_N|keyword|source|…|device|os|browser|language&from&to&campaign&currency&subid&country&offer&stream` — CSV (UTF-8 с BOM для Excel): `group,clicks,conversions,revenue,cost,cr,epc,rpm,uniqueClicks,leads,sales,rejected,pendingRevenue,profit,roi`. Суммы в выбранной валюте, баер получает только свои кампании, значения, начинающиеся с `=`, `+`, `-`, `@`, экранируются от выполнения как формулы.

## Устройства, ОС, браузеры, языки

Клик хранит `device`, `os`, `browser`, `language`. `GET /stats/params?field=device|os|browser|language` группирует по ним так же, как по sub_id (в /admin — пресеты отчёта «Устройство», «ОС», «Браузер», «Язык»).

## Уникальные клики

Клик уникален для кампании, если с тех же IP и User-Agent в неё не кликали за `uniquenessHours` (по умолчанию 24, 1–720). В клик пишутся `uniqueCampaign`, `uniqueStream`, `uniqueGlobal` (PG: `is_unique_*`), отчёты отдают `uniqueClicks`. Проверка идёт по кэшу в памяти (до 300 тыс. посетителей), после перезапуска первый повторный визит снова считается уникальным. Не путать с `dedupeWindow`: тот повторный клик вообще не записывает.

## Привязка посетителей

Как «Привязка посетителей» в Keitaro. Поле кампании `bindVisitors`: `"off"` (по умолчанию), `"stream"` или `"stream_offer"`; `bindTtlHours` — срок привязки в часах (по умолчанию 24, 1–720), считается от последнего визита. Посетитель определяется так же, как для уникальности: IP + User-Agent.

- `stream`: вернувшийся посетитель в пределах срока попадает в тот же поток (оффер и лендинг внутри потока выбираются по весам как обычно).
- `stream_offer`: тот же поток, тот же оффер и тот же лендинг (если лендинг ещё есть в потоке).

Привязка срабатывает, только если поток всё ещё включён, подходит посетителю по условиям и в нём есть рабочий оффер; для `stream_offer` ещё и сам привязанный оффер не в капе кликов/конверсий без запасного и не в архиве. Иначе — обычный выбор потока, и привязка перезаписывается. Привязанный поток выигрывает и у принудительных потоков. Поток узнаётся по позиции и имени: если потоки переставили или переименовали, привязка сбрасывается.

Привязки хранятся в памяти (LRU до 300 тыс. посетителей), без БД: после перезапуска трекера они сбрасываются, следующий визит привязывается заново. В /admin — «Привязка посетителя» (Нет / К потоку / К потоку и офферу) и «Срок привязки, часов» в редакторе кампании. `POST /api/simulate` с `ip` и `userAgent` показывает в `steps[].binding` `{ applies, mode, stream, offerId, landingId, boundAt }` или причину, почему привязка не сработает; без `ip`+`userAgent` привязка не проверяется.

## Кампании баеров

У кампании есть `ownerId` (id пользователя). Баер создаёт кампании только на себя, видит и правит только свои: `/api/campaigns`, `/stats*`, `/api/clicks`, `/api/conversions`, `/api/audit` отдают ему только его данные, а запрос чужой кампании → `403 campaign_not_yours`. Владелец (и `ADMIN_TOKEN`) видит всё и назначает баера полем `ownerId` (в /admin — «Баер» в редакторе кампании). Кампании без баера видит только владелец. На дашборде владельца — таблица «Баеры»: кампании, клики, доход, расход, прибыль и заработок по доле. Офферы и лендинги общие для команды.

## Источники, партнёрские сети и управление сущностями

- Источники трафика: `GET/POST /api/sources`, `PATCH /api/sources/:id`. Источник содержит `name`, `paramMap`, `costModel`, `cpc`, `costFromParam`, `postbackUrl`, `postbackStatuses` (см. «Постбэк в источник трафика»); данные сохраняются в JSON fallback или PostgreSQL.
- Партнёрские сети: `GET/POST /api/networks`, `PATCH /api/networks/:id`. Оффер связывается через `networkId`; сеть хранит параметры click ID и payout для настройки postback.
- При создании кампании с `sourceId` его параметры стоимости и `paramMap` подставляются автоматически, если не указаны вручную.
- Архивирование: `PATCH /api/campaigns/:id` или `/api/offers/:id` с `{ "archived": true }`. Клонирование: `POST /api/campaigns/:id/clone` и `POST /api/offers/:id/clone`.

- `GET /api/audit?entity=campaign|offer|landing|user|settings|api_key&id=&limit=` — кто, когда и что изменил (новые сверху): создание и правки кампаний, потоков, офферов, лендингов, пользователей, входы, автопауза по капу (`actor: system`). Пароли не пишутся. В редакторе кампании — кнопка «История».
- `GET /api/settings`, `PATCH /api/settings { buyerSharePct }` (только владелец, 0–100, по умолчанию 35). Дашборд показывает «Заработок баера» = процент от чистой прибыли (доход − расход) за выбранный период/кампанию в выбранной валюте; при убытке — 0. Владелец меняет процент кликом по плитке.
- Цели: `PATCH /api/settings { dailyRevenueGoal, dailyProfitGoal }` — дневной план команды по доходу и прибыли в базовой валюте (`DEFAULT_CURRENCY`); число ≥ 0 или `null` (нет цели), только владелец. Поля PATCH независимы: можно менять только цели или только `buyerSharePct`. Хранятся на сервере в `settings.json` рядом с `buyerSharePct`, а не в браузере. Владелец задаёт их кнопкой «Цели» на дашборде. Когда выбран период «Сегодня», плитки «Доход» и «Прибыль» показывают полоску прогресса и подпись «73% плана» (от 100% — зелёное «план выполнен»); цель пересчитывается в выбранную валюту по `/api/rates`. С фильтром по кампании прогресс считается по её доходу/прибыли. Баеры видят полоску относительно цели команды (по своим кампаниям), но менять цели не могут; за другие периоды полоски нет.

## Валюты

Сумма конверсии хранится в той валюте, в которой её прислала партнёрка (`&currency=USD`); без валюты — `DEFAULT_CURRENCY` (по умолчанию EUR). Расход кликов (CPC) и кап дохода кампании задаются в `DEFAULT_CURRENCY`.

Отчёты пересчитывают всё в выбранную валюту по текущему курсу: `/stats?currency=RUB`, `/stats/timeseries?currency=USD`, `/stats/params?currency=…` (ответ содержит `currency`). Курсы — `open.er-api.com` (ExchangeRate-API, 160+ валют, без ключа), обновляются каждые 12 часов и кэшируются в `DATA_DIR/fx-rates.json`; при недоступности источника используются последние известные. `GET /api/rates` — курсы и время обновления. `FX_REFRESH=0` отключает загрузку (тесты). В /admin переключатель валюты на дашборде и на страницах со статистикой, под плитками — курс пересчёта. Ссылка «Rates By Exchange Rate API» в меню — условие использования источника.

## Статусы конверсий

`/postback?...&status=lead|sale|rejected|trash` (как в Keitaro). Синонимы партнёрок: `pending`/`hold` → lead, `approved`/`confirmed`/`paid` → sale, `declined`/`cancelled`/`refund`/`chargeback` → rejected, `fraud`/`duplicate` → trash; неизвестный статус → 400. Без `status` — продажа (как раньше).

- Повторный постбэк с другим статусом обновляет конверсию (lead → sale, sale → rejected); тот же статус ещё раз → `409 conversion_already_recorded`. Если в обновлении нет `revenue`, сохраняется сумма из прошлого постбэка. Окно конверсии проверяется только для первой.
- Отчёты: `conversions` = лиды + продажи, `revenue` = только продажи, `pendingRevenue` = сумма лидов, плюс `leads`, `sales`, `rejected`, `trash`. Кап дохода считает только продажи.
- S2S-постбэк оффера получает макрос `{status}` и вызывается на каждое изменение статуса.

## Постбэк в источник трафика

Как «Постбэк в источник» в Keitaro: трекер сам сообщает рекламной сети о конверсии (FB/TikTok/push-сети по своему click id).

- Источник: `postbackUrl` (только `https://`) и `postbackStatuses` — подмножество `lead`, `sale`, `rejected`, `trash`, по умолчанию `["sale"]`. Кампания может переопределить: `sourcePostbackUrl`, `sourcePostbackStatuses` (`null` / `[]` — брать из источника; каждое поле отдельно). Без источника кампания может задать свой URL.
- Макросы (значения URL-кодируются, неизвестные `{…}` остаются как есть): `{click_id}` (наш), `{external_id}` (click id рекламной сети — например, fbclid из ссылки), `{sub_id_1}`…`{sub_id_30}`, `{keyword}`, `{source}`, `{creative_id}`, `{ad_campaign_id}`, `{subid}`, `{campaign}`, `{offer_id}`, `{country}`, `{cost}`, `{status}`, `{revenue}`, `{payout}` (= revenue), `{currency}`.
- Отправляется `GET` при каждом изменении статуса конверсии, если статус в списке, — **один раз на пару (клик, статус)**: повтор `sale` после `rejected` второй раз не уходит. Ответ `/postback` не ждёт отправки (fire-and-forget). До 3 попыток с паузой 0,5 и 1 с: повторяются сетевые ошибки, 5xx и 429; другой 4xx — окончательный. Редиректы не выполняются, таймаут попытки 10 с. Незавершённые повторы теряются при перезапуске процесса.
- Итог пишется в журнал событием `source_postback`: `{ clickId, campaign, status, httpStatus, error, attempts, url }`, где `url` — без query string (там токены и данные посетителя).
- SSRF-защита при каждой отправке: только http(s); хост разрешается через DNS и проверяется адрес, к которому идёт подключение — приватные, loopback, link-local, CGNAT, multicast, IPv4-mapped IPv6 и NAT64 отклоняются (`private_address_refused`). `SOURCE_POSTBACK_ALLOW_PRIVATE=1` (только тесты) разрешает loopback (127.0.0.0/8, ::1) и `http://` в настройках.
- `POST /api/sources/postback-test { url, status? }` — «Тестовый постбэк»: один запрос на URL с тестовыми значениями макросов, ответ `{ ok, httpStatus, error, url }`. Только владелец (или админ-ключ).
- Баер видит `postbackUrl` источника без query string (`postbackUrlMasked: true`) и не может его менять; URL своей кампании видит и меняет.
- В /admin: вкладка «Постбэк» в окне источника и поля «Постбэк в источник» / «Статусы постбэка в источник» в редакторе кампании, кнопка «Тестовый постбэк» показывает HTTP-статус.
- PostgreSQL: колонки `sources.postback_url`, `sources.postback_statuses` (`npm run migrate`); настройки кампании хранятся в её `config`.

## Лендинги

Поток может вести посетителя сначала на лендинг, потом на оффер (как схема «Лендинги и офферы» в Keitaro).

- `POST /api/landings` `{ id, name, url }` (https), `PATCH /api/landings/:id`, `GET /api/landings`.
- В потоке: `"landings": [{ "landingId": "lp-a", "weight": 1 }]` рядом с `offers`. При клике выбираются лендинг и оффер (по весам), посетитель уходит на URL лендинга с `click_id`.
- Кнопка лендинга ведёт на `<трекер>/lp/click?click_id=<click_id>` — трекер отправит на выбранный оффер с тем же click_id и параметрами исходного клика, так что постбэки партнёрки работают как обычно. Готовую ссылку можно передать в лендинг макросом `{lp_click_url}`: `https://лендинг/?go={lp_click_url}`.
- Отчёты: группа `byLanding`, метрики `lpClicks` (уникальные переходы с лендинга) и `lpCtr`.
- Если у потока «Считать клики: нет», клик не записан и `/lp/click` его не найдёт — для потоков с лендингами учёт кликов нужен.

## Параметры и расход

Каждый клик сохраняет параметры источника: `keyword`, `source`, `external_id`, `creative_id`, `ad_campaign_id`, `sub_id_1`…`sub_id_30` (поле `params` в журнале) и расход (`cost`).

- `paramMap` кампании переименовывает параметр в ссылке: `{"sub_id_1":"ad_id","cost":"bid"}` → значение `?ad_id=` попадёт в `sub_id_1`. Недопустимые имена отбрасываются.
- `costModel: "cpc"` + `cpc: 0.12` — фиксированная цена клика; `costFromParam: true` — брать из параметра `cost` (или переименованного), при отсутствии/ошибке — `cpc`.
- Все отчёты отдают `cost`, `profit`, `roi`. `GET /stats/params?field=sub_id_1&campaign=&from=&to=` — отчёт по значениям параметра.
- Макросы в URL оффера: `{sub_id_N}`, `{keyword}`, `{source}`, `{external_id}`, `{creative_id}`, `{ad_campaign_id}`, `{cost}`. Значения URL-кодируются.

### Обновление расходов (Keitaro «Обновить расходы»)

`POST /api/costs { campaign, from, to, tz, amount, currency, filters, uniqueOnly }` — сумма (в `currency`, по умолчанию `DEFAULT_CURRENCY`) переводится в `DEFAULT_CURRENCY` и делится поровну между кликами кампании за локальные даты `from..to` в поясе `tz`; остаток округления — на последний клик, сумма точная. Новый расход **заменяет** прежний расход этих кликов. `filters` — точные значения: `offer`, `stream` и любой параметр клика (`source`, `keyword`, `external_id`, `creative_id`, `ad_campaign_id`, `sub_id_1`…`sub_id_30`); `uniqueOnly` — только уникальные клики. Боты — не клики, расход не получают. Баер — только свои кампании (`403 campaign_not_yours`), «Только чтение» — `403 read_only`. Каждое обновление пишется в журнал (`cost_update`) и в историю (`entity=costs`).

В /admin → «Кампании» → кнопка «€» в строке («Обновить расходы»): период, часовой пояс, сумма и валюта, фильтры, «Только уникальные клики». После — тост «Распределено N кликов, X €» и перезагрузка таблицы. Кнопки нет у роли «Только чтение» и у баера на чужой кампании.

### Импорт расходов Facebook (CSV)

Токены FB не покидают профиль AdsPower владельца, поэтому интеграции с Graph API здесь нет — только файл. В Ads Manager: отчёт с разбивкой **по дням** и колонкой ID (группы объявлений, объявления или кампании) → «Экспорт» → CSV. В /admin → «Кампании» → «Импорт расходов»:

- файл разбирается в браузере: кавычки, разделитель `,` / `;` / табуляция, BOM, десятичная запятая (`3,50`, `1 234,56`), даты `2026-10-28` и `28.10.2026`. Заголовки на английском и русском: `Day` / `Reporting starts` / `Дата начала отчётности`, `Reporting ends` / `Дата окончания отчётности`, `Ad set ID` / `Ad ID` / `Campaign ID` / `ID группы объявлений` / `ID объявления` / `ID кампании`, `Amount spent (EUR)` / `Потраченная сумма (EUR)` (валюта берётся из заголовка, иначе выбирается);
- сопоставление: колонка ID → параметр клика, в котором этот ID приходит в ссылке (напр. `sub_id_2={{adset.id}}` → `sub_id_2`, ID кампании → `ad_campaign_id`); одна или несколько кампаний Umbrella; часовой пояс кабинета;
- предпросмотр: каждая строка со статусом. Строки за несколько дней, без ID (итоги) или с неверной суммой не отправляются, но видны в таблице. После «Применить» видно, сколько кликов получила каждая строка; строки без кликов помечены «нет кликов».

`POST /api/costs/import { campaign: id | [ids], param, tz, uniqueOnly?, rows: [{ date, id, amount, currency }] }` (до 5000 строк): каждая строка — обновление расходов за этот день с фильтром `param = id`; при нескольких кампаниях сумма делится между кликами всех кампаний. Ответ: `{ applied, failed, clicks, cost, costCurrency, results: [{ row, date, id, amount, currency, clicks, cost, replaced?, merged?, error? }] }`; `error` строки: `invalid_date`, `invalid_id`, `invalid_amount`, `invalid_currency`, `no_matching_clicks`. Права — как у `/api/costs`, в историю пишется действие `import`.

**Повторный импорт не удваивает расход.** Ключ импорта `кампании|param|id|дата` хранится в событии `cost_update` (`importKey`), а в PostgreSQL ещё и в таблице `cost_imports` (ключ → клики последнего импорта; нужна `node src/migrate.js`). Повторный импорт того же ключа заменяет прежний: клики получают новую долю, а клики прежнего импорта, которые больше не подходят (другой пояс, параметр клика изменил постбэк), сбрасываются в 0 отдельным событием `cost_update` с `importReset`. Строки с одинаковым ключом в одном запросе суммируются (выгрузка с разбивкой по площадкам). Ключ без кликов, которого раньше не было, не сохраняется. Ручное «Обновить расходы» и импорт пишут в одно поле `cost` клика: действует последнее.

## Мониторинг офферов и лендингов

`src/monitor.js` раз в `MONITOR_INTERVAL_MS` (по умолчанию 10 минут) проверяет каждый URL оффера, лендинга и потока «Прямой URL» в активных кампаниях: GET с обычным браузерным User-Agent, до 5 редиректов, таймаут 10 с на всю цепочку. Макросы подставляются пустыми, `{click_id}` и `{subid}` — значением `monitor-check`. Цель «не отвечает» после двух неудачных проверок подряд (ошибка сети, таймаут или итоговый статус ≥ 400) и снова «отвечает» после одной успешной.

Настройка кампании `monitoring` (POST/PATCH, в редакторе — «Мониторинг офферов»):

- `notify` (по умолчанию) — событие `monitor` в журнале (`campaign`, `stream`, `target` вида `offer:id` / `landing:id` / `url`, `url` без query string, `status`, `error`) и запись в «Историю» кампании от `system`; одно событие на каждое падение, без повторов, пока цель лежит;
- `disable` — то же, плюс поток выключается (`enabled: false`, `disabledBy: "monitor"`, запись `disable_stream` в истории). Когда все цели потока снова отвечают, монитор включает его обратно (`enable_stream`). Потоки, выключенные вручную, монитор не трогает и не проверяет; включённый вручную поток с лежащим оффером не выключается повторно до следующего падения;
- `off` — кампания не проверяется.

`GET /api/monitor` → `{ enabled, intervalMs, targets: [{ url, ok, status, error, checkedAt, downSince, failures, campaigns: [{ campaign, name, stream, target, mode }] }] }`, состояние в памяти (после рестарта счётчик неудач начинается заново, `disabledBy` хранится в потоке). `POST /api/monitor/check` — проверить сразу (только владелец). На дашборде /admin блок «Не отвечают» со ссылками на кампании появляется, только пока что-то лежит.

Защита от SSRF: только `http`/`https`; имя хоста резолвится, и если хоть один адрес приватный (loopback, 10/8, 172.16/12, 192.168/16, 169.254/16 и metadata, 100.64/10, IPv6 ULA/link-local, multicast) — запрос не делается, в том числе на любом шаге редиректа. Соединение идёт ровно на проверенный адрес (без повторного DNS). `MONITOR=0` выключает таймер (ручная проверка работает); тесты запускают сервер с `MONITOR=0`. `MONITOR_ALLOW_PRIVATE=127.0.0.1` — список адресов-исключений только для тестов, в production не задавать.

## Импорт офферов из Keitaro

`node scripts/import-keitaro-offers.mjs` — только чтение Keitaro. Без флагов показывает группы и партнёрки; `--groups`, `--networks`, `--ids` выбирают офферы; `--apply` записывает в Umbrella (`kt-<id>`, повторный запуск обновляет). Ключи — из `~/.keitaro-api-key` и `~/umbrella-admin-token.txt`. Макросы Keitaro переводятся (`{subid}` → `{click_id}`, `{campaign_id}` → `{campaign}`), неподдерживаемые удаляются с предупреждением.

## Пользователи и доступ

У Umbrella своя база пользователей (таблицы `users`, `sessions` или файлы в `DATA_DIR`), не связанная с другими проектами на том же домене. Роли: `owner` (управляет пользователями), `buyer` (кампании, офферы, отчёты) и `viewer` (только чтение, см. «Права пользователей»).

- Первый запуск: `/admin` предлагает создать владельца. Если задан `ADMIN_TOKEN`, без него владельца не создать — чужой не займёт свежую установку.
- `REQUIRE_LOGIN=1` закрывает отчёты и API для анонимов; трекинг (`/r`, `/postback`) остаётся публичным.
- Скрипты могут по-прежнему ходить с `Authorization: Bearer <ADMIN_TOKEN>`.

### Личные API-ключи

Вместо общего `ADMIN_TOKEN` у каждого пользователя могут быть свои ключи (/admin → «API-ключи»). Ключ работает от имени своего пользователя: та же роль и те же кампании, что в его сессии — ключ баера видит только свои кампании (`403 campaign_not_yours` на чужие), ключ владельца — всё.

- `POST /api/keys {name}` — создать ключ (нужен вход в аккаунт). Ответ `{ key, secret }`: секрет вида `umb_<32 случайных байта base64url>` показывается **один раз**. Сохраняются только SHA-256 секрета и последние 4 символа; восстановить ключ нельзя — потерянный удалите и создайте новый. Ключом нельзя создать другой ключ (`403 session_required`).
- `GET /api/keys` — свои ключи (`id`, `name`, `last4`, `createdAt`, `lastUsedAt`); владелец с `?all=1` видит ключи всей команды. Секрет не возвращается.
- `DELETE /api/keys/:id` — удалить свой ключ; владелец может удалить любой. Удаление пользователя удаляет и его ключи.
- Запросы: `Authorization: Bearer umb_…`. Неверный или удалённый ключ → `401 invalid_api_key`. Заголовок `X-Requested-With` не нужен. `lastUsedAt` обновляется не чаще раза в минуту.
- Хранение: таблица `api_keys` в PostgreSQL (`node src/migrate.js`), без БД — `DATA_DIR/api_keys.json`. Создание и удаление ключей пишутся в журнал (`entity=api_key`), секрет — никогда.

### Права пользователей

Как «Права пользователей» в Keitaro: владелец задаёт их в /admin → «Пользователи» (кнопка ✎ в строке или при создании). Всё проверяется на сервере — скрытая кнопка в панели только убирает лишнее с экрана. На владельца и `ADMIN_TOKEN` флаги не действуют. Ключ API работает с правами своего пользователя.

- Роль `viewer` («Только чтение»): видит то же, что баер, — свои кампании (`ownerId`) со статистикой, журналами и офферами; с флагом `viewAll: true` — все кампании команды. Любой не-GET запрос к `/api/*`, `/stats*` → `403 read_only` (в том числе создание API-ключей); вход и выход (`/api/auth/*`) работают. Смены своего пароля в Umbrella пока нет.
- `hideRevenue: true` («Скрывать доход»): из ответов `/stats*`, `/api/conversions`, `/api/offers`, `/api/audit`, `/api/simulate` сервер **удаляет** (а не обнуляет — нулевая прибыль или ROI были бы ложью) поля дохода: `revenue`, `pendingRevenue`, `profit`, `roi`, `epc`, `uepc`, `rpm`, `payout*`, `*earning*` на любой глубине; из `/api/offers`, `/api/audit` и `/api/simulate` — также `url` и `postbackUrl` офферов. CSV `/stats/export` выгружается без этих колонок (расход `cost` остаётся). `/dashboard` перенаправляет в `/admin`.
- `offersAccess: 'own'` («Только офферы своих кампаний»): `GET /api/offers` отдаёт только офферы из потоков доступных пользователю кампаний; правка и копирование чужого оффера → `404 offer_not_found`, создание оффера с занятым чужим id → `409 offer_id_taken`. По умолчанию `'all'`.
- API: `PATCH /api/users/:id { role, hideRevenue, offersAccess, viewAll }` (только владелец; свою роль менять нельзя — `409 cannot_change_own_role`, последнего владельца понизить нельзя — `409 last_owner`); те же поля принимает `POST /api/users`. `GET /api/auth/me` и `GET /api/users` отдают их у пользователя. Изменения пишутся в журнал (`entity=user`) и действуют со следующего запроса.
- Хранение: колонки `hide_revenue`, `offers_access`, `view_all` таблицы `users` (`node src/migrate.js`), без БД — те же поля в `DATA_DIR/users.json`.

### Доступ к панели по IP (`ADMIN_ALLOWED_IPS`)

`ADMIN_ALLOWED_IPS=203.0.113.7,198.51.100.0/24` — IP или IPv4 CIDR через запятую. Если задано, панель (`/admin`), `/api/*`, `/stats*` и `/dashboard` отвечают `403 admin_ip_not_allowed` всем остальным адресам — даже с верным паролем, ключом или `ADMIN_TOKEN`. Трекинг (`/r/…`, `/lp/click`, `/postback`, `/health`) не ограничивается никогда. IP клиента берётся по правилам `TRUST_PROXY` (за nginx нужен `TRUST_PROXY=1`, иначе все запросы придут с IP прокси). Пусто — ограничения нет. Невалидное правило останавливает запуск сервера, чтобы опечатка не открыла панель.

Настраивается только переменной окружения, не из панели — так никто не запрёт команду кнопкой. На странице «Пользователи» видно текущее состояние и ваш IP (`GET /api/security`, только владелец). Перед включением на проде проверьте свой IP там же: при ошибке доступ возвращается только правкой env на сервере.

## GeoIP

Страна посетителя определяется по базе DB-IP Country Lite (`GEOIP_DB=/путь/к/файлу.mmdb`, читается через `@maxmind/geoip2-node`). Деплой скачивает базу на сервер в `/opt/umbrella/geo/country.mmdb` и обновляет раз в 30 дней; при сбое загрузки остаётся прежняя. Без базы страна неизвестна: гео-фильтры кампаний пропускают всех, потоки с условием по стране не срабатывают. `/health` показывает `geo: true|false`. Лицензия CC BY 4.0 — ссылка «IP Geolocation by DB-IP» в панели обязательна. Тест с настоящей базой: `GEOIP_TEST_DB=/путь/dbip.mmdb npm test`.

Провайдер посетителя — по базе DB-IP ASN Lite (`GEOIP_ASN_DB`, на сервере `/opt/umbrella/geo/asn.mmdb`, обновляется так же). В клик пишутся `asn`, `isp` и `datacenter` (провайдер похож на облако/хостинг: AWS, Google Cloud, Azure, OVH, Hetzner…). Отчёт «Провайдер» — `/stats/params?field=isp`. `/health` показывает `isp: true|false`. Тест: `GEOIP_TEST_ASN_DB=/путь/dbip-asn.mmdb npm test`.

Тип соединения (Keitaro «Тип соединения», WiFi / Mobile) — поле клика `connection` (колонка `connection` в PostgreSQL): `mobile`, `datacenter`, `broadband` или `null`, если базы ASN нет или IP в ней не найден. Это эвристика по ASN, а не измерение. `mobile` — сеть из короткого списка чисто мобильных ASN (`src/connection-type.js`: T-Mobile USA, Verizon Wireless, AT&T Mobility, Sprint, Free Mobile, Vodafone UK, O2 UK, EE, Three UK, Airtel mobile) или организация, в названии которой есть mobile / wireless / cellular / GPRS / LTE / 3G, 4G, 5G. `datacenter` — как флаг `datacenter`. Всё остальное — `broadband`. Список ASN нужен, потому что DB-IP называет часть мобильных сетей по материнской компании («Verizon Business», «AT&T Enterprises»). Смешанные операторы, у которых домашний интернет и мобильная сеть в одной AS (Orange, SFR, Bouygues, Deutsche Telekom, Vodafone в большинстве стран), обычно считаются `broadband` — мобильный трафик через них так не отличить. И наоборот: местный провайдер радиодоступа с «Wireless» в названии попадёт в `mobile`. Условие потока `connections: ["mobile"]` работает с «НЕ» (`not: ["connections"]`) и в «Проверить маршрут» (поле `connection` в `/api/simulate` задаёт тип вручную); при неизвестном типе условие не срабатывает (с «НЕ» — срабатывает). Отчёт — группировка «Тип соединения», `/stats/params?field=connection`.

## Лог-файл (LOG_FILE)

По умолчанию логи идут только в stdout/stderr. На проде их уже собирает journald (`journalctl -u umbrella`), там `LOG_FILE` не нужен. Для Docker и других хостов без journald задайте `LOG_FILE=/путь/umbrella.log`: всё, что приложение пишет через `console.log/warn/error`, дополнительно дописывается в файл строками вида `2026-10-30T12:00:00.000Z WARN  [db] …` (время UTC, уровень INFO/WARN/ERROR). Ротация по размеру: при превышении `LOG_MAX_MB` (по умолчанию 50) файл становится `.1`, старые сдвигаются в `.2` и `.3`, самый старый удаляется — на диске не больше 4 × `LOG_MAX_MB`. Ошибка записи (диск полон, нет прав) не роняет трекер: одно предупреждение в stderr. Приложение не печатает секреты (токены, пароли, `DATABASE_URL`), поэтому их нет и в файле; новые сообщения должны соблюдать то же правило.

## Домены трекинга

Свои домены для ссылок (как «Домены» в Keitaro): впишите домен в `deploy/domains.txt` и направьте его DNS A-запись на сервер. Деплой проверит DNS, создаст блок nginx (наружу только `/r/…`, `/lp/click`, `/postback`, `/health`) и выпустит сертификат Let's Encrypt. Домен, который не смотрит на сервер, пропускается с предупреждением. `PRIMARY_HOST` (на проде `nespizdili.lol`) — хост панели; на любом другом хосте приложение отдаёт только трекинг и без `BASE_PATH` (`https://track.example.com/r/<кампания>`). У кампании поле `domain` — ссылки в /admin строятся на нём. `GET /api/domains` — список доменов.

## TRUST_PROXY

По умолчанию IP посетителя — адрес TCP-соединения, а `X-Forwarded-For` игнорируется: его может прислать любой клиент и обойти списки IP, уникальность и rate limit. Если перед трекером стоит свой прокси (nginx, Caddy, балансировщик), задайте `TRUST_PROXY=1` (или число своих прокси в цепочке). Тогда IP берётся из `X-Forwarded-For` справа — адрес, который дописал ваш прокси, а не тот, что прислал клиент. Без этой настройки за прокси у всех кликов будет IP прокси, и уникальность с rate limit начнут резать нормальный трафик.

В `/dashboard` доступен редактор потоков: выберите кампанию, добавьте потоки, условия и офферы с весами, затем нажмите «Сохранить потоки». Существующие плоские потоки также редактируются. Пустой список отключает stream-маршрут кампании. Если задан `ADMIN_TOKEN`, укажите его в раскрывающемся поле редактора; он хранится только в памяти страницы. Ошибки сохранения показываются рядом с формой.

Кампания также может ограничивать всю свою аудиторию через `allowOS` и `allowBrowsers` в POST/PATCH. Например, `{"allowOS":["ios"],"allowBrowsers":["safari"]}`. Пустые массивы снимают ограничения. Правила действуют для обоих tracking-маршрутов.

## Статистика потоков

`GET /stats?campaign=campaign-id&stream=stream-name` фильтрует по имени потока. Клики по явному `/r/:campaign/:offer` и старые клики без имени относятся к `default`. Ответ всегда содержит `byStream` вместе с `byCampaign`, `byCountry`, `byOffer`; все срезы содержат clicks, conversions, revenue, cr, epc и rpm. В панели добавлены поле «Поток» и таблица потоков.

CR в API — доля (`0.25` = 25%), EPC = revenue / clicks, RPM = revenue × 1000 / clicks. При нуле кликов метрики равны нулю. Статистика периода относится к выбранным кликам и связанным с ними конверсиям. Revenue сохраняет прежнюю семантику: суммы разных валют пока не пересчитываются по курсу.

`npm test` запускает проверки общего расчёта отчётов и HTTP smoke-тест. Дополнительный тест `node test/stream-editor-ui.mjs` проверяет реальную панель в Playwright, если он установлен. Можно указать `PLAYWRIGHT_MODULE` с абсолютным путём существующей установки Playwright. Тест использует отдельный порт 4212 и временные данные.

Настройки кампании (POST/PATCH `/api/campaigns`):

- `botFilter: true` — запросы с пустым или ботовым User-Agent (краулеры, headless, curl, python-requests и т. п.) не считаются кликами: пишутся в журнал как событие `bot` и редиректятся на тот же оффер без `click_id`. Отдельной страницы для ботов нет намеренно.
- `datacenterAsBot: true` — так же обрабатываются клики из сетей дата-центров (нужна база провайдеров): тот же оффер, событие `bot` с `reason: datacenter`, в статистику не попадают.
- `conversionWindowDays: N` (1–365) — постбэк на клик старше N дней отклоняется с `409 conversion_window_expired`. `null` — без ограничения.
- `blockedIps: [...]` / `allowedIps: [...]` — точный IP (IPv4/IPv6) или IPv4 CIDR (`198.51.100.0/24`). Блок → `403 ip_blocked`; есть whitelist и IP не в нём → `403 ip_not_allowed`. Невалидные правила отбрасываются. IP клиента определяется по правилам `TRUST_PROXY` (см. ниже).
- `totalCap: N` — общий лимит кликов кампании за всё время; на N-м клике кампания ставится на паузу (`active: false`, событие `campaign_paused`), дальше `capUrl` или `429 total_cap_reached`.

Настройки оффера (POST/PATCH `/api/offers`): `dailyCap: N` — дневной лимит кликов на оффер по всем кампаниям. При потоковой маршрутизации капнутый оффер пропускается в ротации; при явном `/r/:campaign/:offer` → `capUrl` кампании или `429 offer_cap_reached`.

## Кап конверсий и запасной оффер

Как «Кап конверсий» + «Альтернативный оффер» в Keitaro. Поля оффера (POST/PATCH `/api/offers`, хранятся в JSON и в PostgreSQL — колонки `conversion_cap`, `cap_tz`, `alt_offer_id`):

- `conversionCap: N` — сколько конверсий в сутки принимает оффер (целое ≥ 1, `null` — без капа);
- `capTz` — часовой пояс суток капа (IANA, по умолчанию `UTC`), сутки начинаются в местную полночь;
- `altOfferId` — запасной оффер (другой существующий оффер или `null`).

Что считается: конверсии со статусом `lead` **и** `sale` (по последнему статусу клика — лид, ставший `rejected`/`trash`, перестаёт считаться) по кликам, записанным с этим оффером, во всех кампаниях; время — первого постбэка клика, начиная с местной полуночи `capTz`. С PostgreSQL счёт идёт запросом `conversions JOIN clicks` по `offer_id`, без базы или при её сбое — по журналу JSONL. Число кэшируется на 30 секунд на оффер, чтобы `/r` не ходил в базу на каждый клик; постбэк по офферу сбрасывает кэш сразу (и ещё раз, когда конверсия дошла до PostgreSQL).

Маршрутизация:

- Оффер с достигнутым капом конверсий и с `altOfferId` отдаёт свой трафик (с тем же весом в потоке) запасному. Цепочка — до 3 переходов (A → B → C → D); запасной в архиве, с капом кликов или конверсий пропускается и берётся его запасной; несуществующий запасной или цикл (A → B → A) обрывают цепочку.
- Нет пригодного запасного — оффер пропускается в ротации, как оффер с капом кликов; если в потоке не осталось офферов, поток не подходит (дальше fallback или `404 no_matching_stream`). При явном `/r/:campaign/:offer` — `capUrl` кампании или `429 offer_conversion_cap_reached`.
- Клик записывается с оффером, на который реально ушёл посетитель, поэтому его конверсии считаются в кап запасного.
- Запасной оффер используется только при капе конверсий; кап кликов (`dailyCap`) просто пропускает оффер.

`POST /api/simulate` показывает это: в `steps[].streams[].cappedOffers` — `{ offerId, reason: archived|click_cap|conversion_cap, altOfferId }`, в `result.destinations` — `{ offerId: <запасной>, insteadOf: <исходный>, share, url }`. В /admin поля — в окне оффера, вкладка «Настройки»: «Кап конверсий в день», «Часовой пояс капа», «Запасной оффер».

## Панель /admin

Интерфейс повторяет разделы и рабочие сценарии Keitaro поверх того же API:

- **Дашборд** — плитки (клики, конверсии, CR, доход, EPC, RPM), график по часам (один день) или по дням, топ кампаний/офферов/потоков/стран, последние клики; фильтр кампании и периода.

## Журналы в dashboard

Секция «Журнал событий» в `/dashboard` переключается между кликами и конверсиями. Доступны фильтры кампании, оффера, имени потока и дат, страницы по 25/50/100 записей, кнопки следующей/предыдущей страницы и обновление. В клике раскрываются IP, путь, реферер и User-Agent. При заданном `ADMIN_TOKEN` укажите его в поле «Доступ к журналу»: токен передаётся заголовком и хранится только в памяти страницы.

Оба log API возвращают одинаковые поля в JSONL/PostgreSQL: `clickId`, `campaign`, `offerId`, `stream`, `at` (ISO UTC); для конверсий также `revenue` (число или null), `currency`. Совместимые aliases `click_id`, `offer_id`, `created_at`, `user_agent` сохранены. Пустой поток обозначается `default`. Данные postback URL и неизвестные поля событий в журналы не включаются.

Ответ имеет вид `{ clicks: [...], limit, offset, hasMore, nextOffset, storage }` или `{ conversions: [...] ... }`. `limit` — целое от 1 до 100 (большее значение ограничивается 100), `offset` — неотрицательное целое. Некорректные параметры возвращают 400. Сортировка: время события по убыванию, затем click ID. При добавлении новых событий между запросами страницы с offset могут сдвигаться.

`from`/`to` задаются реальными календарными датами `YYYY-MM-DD`; `to` включает день до последней миллисекунды UTC. В журнале конверсий даты относятся к времени конверсии, а фильтры campaign/offer/stream — к исходному клику. Это отличается от `/stats`, где период относится к выбранным кликам.

`test/ui/*.mjs` — браузерные проверки `/admin` по разделам (`streams`, `offers`, `dashboard`, `reports`, `report-metrics`, `campaigns-list`, `costs`, `click-log`, `monitor`, `mobile`, `accounts`, `permissions`, `source-postback`), см. «Браузерные тесты панели». Требуют Playwright или `PLAYWRIGHT_MODULE`.

`node test/event-logs-ui.mjs` — дополнительный браузерный тест фильтров, пагинации, прав доступа и мобильной таблицы. Требуется установленный Playwright или `PLAYWRIGHT_MODULE` с путём к существующей установке. Тест работает на отдельном порту 4213 с временными событиями.

## Надёжность postback

В одном процессе Node одновременные postback одного `click_id` выполняются последовательно: первая успешная запись получает 200, повторы — `409 conversion_already_recorded`. JSONL проверяется даже если асинхронное PostgreSQL-зеркало ещё не видит конверсию. Перезапуск сохраняет защиту благодаря журналу. Сбой записи не принимает конверсию и оставляет возможность повторить запрос. JSONL-каталог должен обслуживаться одним процессом; эта блокировка не предназначена для нескольких серверов/cluster workers.

`revenue` — неотрицательная десятичная сумма до `99999999.9999`, максимум четыре знака после точки (как `NUMERIC(12,4)`). Экспоненты, hex, отрицательные и нечисловые значения получают 400. `currency` — три буквы, приводится к верхнему регистру. Пустые значения сохраняются как null; ноль остаётся нулём и в S2S-макросах. Некорректный UUID получает `400 invalid_click_id`, неизвестный UUID — 404.

`conversionWindowDays` проверяется по исходному времени клика. При включённом окне неизвестное/повреждённое время отклоняется; на самой границе окно ещё действует, позже — `409 conversion_window_expired`. S2S запускается только после записи и не повторяется для дубликатов. Он остаётся fire-and-forget с таймаутом 10 секунд: гарантированная доставка с повторными попытками требует отдельной очереди.

Зеркалирование PostgreSQL сохраняет порядок click → conversion для каждого click ID и исходные timestamps. Разные клики записываются параллельно. Остановка сервера дожидается очереди зеркалирования перед закрытием пула. Неудачные записи остаются в JSONL; автоматический replay в PostgreSQL пока не добавлен.

## Браузерные тесты панели

`test/ui/*.mjs` и `test/*-ui.mjs` (Playwright + Chromium) не входят в `npm test`: их гоняет отдельный job `ui` в CI, деплой ждёт его. Каждый файл `test/ui/*.mjs` поднимает свой сервер с пустым каталогом данных и свой браузер через общий помощник `test/ui/setup.mjs`, поэтому файлы независимы и идут параллельно. Новую проверку панели добавляйте отдельным файлом в `test/ui/` (или блоком в подходящий файл), не опираясь на данные других файлов. Локально: `npm install --no-save playwright && npx playwright install chromium` (или `PLAYWRIGHT_MODULE=/путь/к/playwright/index.mjs`), затем `npm run test:ui` или один файл: `node test/ui/offers.mjs`.

## Проверка на PostgreSQL

CI поднимает чистый PostgreSQL (job `postgres`): миграции с нуля дважды, затем `test/postgres*.test.mjs` — данные, записанные сервером, должны вернуться из базы после перезапуска с пустым каталогом данных. Локально: `docker run -d --name umb-pg -e POSTGRES_USER=umbrella -e POSTGRES_PASSWORD=local -e POSTGRES_DB=umbrella -p 55432:5432 postgres:16-alpine`, затем `DATABASE_URL=postgresql://umbrella:local@127.0.0.1:55432/umbrella node src/migrate.js` и `TEST_DATABASE_URL=… node --test test/postgres-e2e.test.mjs`.
Для production задайте `REQUIRE_POSTGRES=1`: тогда приложение не стартует при недоступной базе и не потеряет события, незаметно переключившись на JSONL.

### Production checklist

1. Задайте `DATABASE_URL`, `REQUIRE_POSTGRES=1`, `REQUIRE_LOGIN=1`, `ADMIN_TOKEN` и `POSTBACK_SECRET` через секрет-хранилище.
2. Выполните миграцию до запуска приложения: `npm run migrate` или используйте Docker Compose, где миграция запускается автоматически.
3. Ограничьте доступ к PostgreSQL сетью приложения, а HTTP наружу отдавайте через HTTPS reverse proxy.
4. Периодически запускайте `DATABASE_URL=... BACKUP_DIR=./backups sh scripts/backup-postgres.sh` и проверяйте восстановление резервной копии на отдельной базе.
5. Проверьте `/health`, `/stats`, тестовый `/r/<campaign>` и postback после деплоя; не публикуйте `ADMIN_TOKEN` и `POSTBACK_SECRET` в логах.

## Бэкапы

Каждую ночь (03:30 UTC, systemd timer `umbrella-backup.timer`) `deploy/backup.sh` делает дамп своей базы (`pg_dump -Fc umbrella`) и архив каталога данных (`/opt/umbrella/data`: журнал событий, настройки). Файлы лежат на сервере в `/opt/umbrella/backups` (доступ только root), хранятся 14 дней. Деплой ставит таймер и сразу делает первый бэкап, если за последние сутки его не было. Восстановление: `pg_restore --clean --if-exists -d umbrella файл.dump` и `tar -xzf файл-data.tar.gz -C /opt/umbrella` при остановленном сервисе.

## Очистка статистики и срок хранения

Как «Очистка статистики» в Keitaro. **Удаление необратимо: вернуть данные можно только из ночного бэкапа** (`deploy/backup.sh`, см. «Бэкапы»: дамп базы + архив каталога данных с журналом; восстанавливать обе части вместе, при остановленном сервисе).

- `POST /api/campaigns/:id/clear-stats` с `{ "confirm": "<id кампании>", "before": "YYYY-MM-DD" }` — только владелец или `ADMIN_TOKEN` (баер → `403 owner_only`). `confirm` должен совпадать с id кампании, иначе `400 confirm_mismatch`. Без `before` удаляются все клики, конверсии, клики по лендингам и боты кампании; с `before` — клики (и боты), записанные раньше этой даты по UTC, вместе с конверсиями и кликами по лендингам этих кликов (даже если конверсия пришла позже). Ответ — `removed`: число удалённых событий журнала и строк PostgreSQL (`postgres`, `null` без базы). В «Историю» пишется запись `clear_stats` с числами.
- В /admin: редактор кампании → блок «Очистить статистику» (виден владельцу и по ключу администратора): «Всё» или «Старше даты», затем ввести id кампании — без этого кнопка не активна.
- `RETENTION_DAYS=N` — раз в сутки (первый раз через `RETENTION_DELAY_MS`, по умолчанию 60 с после старта) удаляются клики старше N дней **без конверсии**, их клики по лендингам и события ботов старше N дней. Клики с конверсией (любого статуса) и сами конверсии хранятся всегда. Итог — в логе сервиса (`[retention] …`) и записью `retention` в «Истории». Без переменной данные хранятся бессрочно; в тестах выключено, пока не задано явно.

Как устроено: удаление идёт из JSONL-журнала (источник истины) и из PostgreSQL. Журнал переписывается потоково во временный файл рядом с ним и атомарно подменяется (`rename`); на время перезаписи новые события (клики, постбэки) ждут — запись в журнал проходит через общий замок (`src/retention.js`), а очередь зеркала PostgreSQL сначала дописывается, чтобы удалённая строка не вернулась. Строки PostgreSQL удаляются в одной транзакции до подмены файла: если база вернула ошибку, журнал не трогается. Трекинг во время очистки не теряет кликов, только ненадолго задерживает ответ. Счётчики капов конверсий сбрасываются.
